# Budget Buddy Interview Guide

프로젝트를 외워서 소개하기보다, 어떤 문제를 발견했고 왜 이 방법을 선택했는지 자신의 말로 설명하기 위한 복습 문서입니다.

## 1. 60초 소개

> Budget Buddy는 거래와 잔액 정합성을 중심으로 만든 Spring Boot 웹 가계부입니다. 거래 저장과 잔액 변경을 하나의 트랜잭션으로 묶고, 같은 사용자의 동시 지출에는 비관적 락을 적용했습니다. 네트워크 재시도로 같은 거래가 두 번 반영되지 않도록 멱등성 키도 사용했습니다. DB 거래와 CSV 행은 공통 분석 모델로 바꿔 동일한 통계 서비스를 재사용하고, 금액 계산은 서버가 BigDecimal로 수행합니다. Gemini는 계산된 집계값만 해석하도록 역할을 제한했습니다. H2 기반 자동 테스트와 로컬 데모 화면을 제공해 누구나 핵심 흐름을 재현할 수 있습니다.

## 2. 가장 중요한 코드 8개

### 1) `TransactionService`

거래 생성의 트랜잭션 경계입니다. 사용자 잠금, 멱등성 확인, 도메인 검증, 잔액 변경, 거래 스냅샷 저장 순서를 설명할 수 있어야 합니다.

### 2) `UserRepository.findByIdForUpdate()`

왜 `@Transactional`만으로 동시성 문제가 해결되지 않는지, `PESSIMISTIC_WRITE`가 같은 사용자 요청을 어떻게 순차 처리하는지 설명합니다.

### 3) `Transaction.balanceBefore / balanceAfter`

현재 잔액만 저장하는 방식과 비교해 특정 등록 작업 전후 상태를 추적할 수 있다는 장점을 설명합니다. `transactionAt`은 실제 발생 시각이고, 스냅샷은 변경을 적용한 `transactionId` 등록 순서 기준입니다. 과거 거래를 나중에 등록해도 과거 잔액을 임의로 다시 쓰지 않는다는 선택과 한계를 함께 설명합니다.

### 4) `AnalysisTransaction`

JPA Entity를 분석 로직에 직접 의존시키지 않고 DB와 CSV가 공유하는 최소 입력 모델을 만든 이유를 설명합니다.

### 5) `AnalysisService`

AI 없이 서버가 `BigDecimal`로 총액, 평균, 기간 비교, 카테고리·월별 집계를 계산합니다. 외부 I/O가 없어 단위 테스트하기 쉽습니다.

### 6) `CsvParserService`와 `CsvMappingService`

인코딩과 구분자가 다른 파일을 읽고, 헤더 별칭과 모호하지 않은 값 패턴으로 컬럼을 자동 연결하는 흐름을 설명합니다. 불확실한 경우만 사용자에게 묻고, 직접 확정한 매핑은 브라우저에 헤더 설정만 저장해 재사용합니다. 자동 분석과 DB 저장을 분리한 이유, 오류를 행 번호와 필드 단위로 반환한 이유도 중요합니다.

### 7) `AiReportService`와 `GeminiClient`

원본 거래 대신 집계 결과를 보내는 이유, API Key를 헤더와 환경변수로 관리하는 이유, 외부 실패를 내부 오류로 변환하는 방식을 설명합니다.

### 8) `SecurityConfig`와 `AuthController`

DB 접속 계정과 애플리케이션 사용자를 구분하고, 세션·BCrypt·CSRF·Principal을 이용해 사용자를 격리한 흐름을 설명합니다.

## 3. 예상 질문과 답변 포인트

### 왜 비관적 락을 선택했나요?

잔액은 앞 거래 결과가 다음 거래 승인 여부에 직접 영향을 줍니다. 충돌 후 재시도하는 낙관적 락보다 같은 사용자 잔액 변경을 짧게 순차 처리하는 방식이 현재 규모에서 단순했습니다. 사용자가 다르면 서로 다른 row를 잠그므로 전체 시스템을 잠그지 않습니다.

### `@Transactional`만 있으면 충분하지 않나요?

각 요청 내부의 원자성은 보장하지만, 두 트랜잭션이 커밋 전 같은 잔액을 읽는 문제까지 자동으로 막지는 않습니다. 그래서 잔액을 읽고 검증하는 시점부터 row lock이 필요했습니다.

### 멱등성 키는 왜 필요한가요?

POST 응답이 유실되면 클라이언트는 성공 여부를 모른 채 재시도할 수 있습니다. 같은 키를 기존 거래와 연결하면 서버 상태 변경은 한 번만 수행하고 이전 성공 결과를 다시 반환할 수 있습니다. 애플리케이션 조회뿐 아니라 DB 유니크 제약도 둬 최종 방어선을 만들었습니다.

### React를 쓰지 않은 이유는 무엇인가요?

현재 화면은 네 개이고 복잡한 전역 상태나 프론트 라우팅이 필요하지 않습니다. 별도 Node 빌드는 CORS와 배포 단위를 추가합니다. 백엔드 설계를 보여주는 프로젝트 목적에 맞춰 Spring Boot 정적 리소스와 ES Module 수준으로 유지했습니다. 화면과 상태가 복잡해지면 React 도입을 다시 검토할 수 있습니다.

### 왜 AI에게 거래 원본을 보내지 않나요?

금액 계산을 LLM에 맡기면 결과가 비결정적이고 검증하기 어렵습니다. 서버가 정확한 집계를 만든 뒤 AI에는 해석에 필요한 요약값만 전달하면 토큰과 데이터 노출 범위를 줄이고 역할을 분리할 수 있습니다.

### CSV와 DB 분석을 어떻게 재사용했나요?

DB Entity와 검증된 CSV 행을 모두 `AnalysisTransaction`으로 변환합니다. 이후 합계와 추이 계산은 같은 `AnalysisService`가 맡습니다. 새 입력 방식이 생겨도 어댑터 역할의 변환만 추가하면 통계 규칙은 유지됩니다.

### H2 테스트만으로 PostgreSQL 락을 보장할 수 있나요?

완전히 보장할 수 없습니다. H2는 빠른 피드백을 맡고, 추가한 Testcontainers 테스트가 같은 롤백·동시 지출·중복 요청 시나리오를 PostgreSQL에서 실행하도록 구성했습니다. 현재 PC는 Docker가 없어 PostgreSQL 테스트가 초기화 단계에서 실패했으며, 실제 실행 확인은 남아 있습니다. 테스트 작성과 검증 완료를 구분해서 설명합니다.

### Docker와 Compose는 각각 왜 필요한가요?

Docker는 정해진 실행환경으로 앱이나 DB를 실행하는 도구입니다. Compose는 둘의 환경변수·네트워크·시작 순서를 한 파일로 묶습니다. 이 프로젝트는 PostgreSQL이 준비된 다음 앱을 시작하고, DB 데이터는 볼륨에 보관합니다. 앱 컨테이너는 `localhost` 대신 서비스 이름 `db`로 DB에 연결합니다.

### 롤백 테스트를 어떻게 작성했나요?

서비스 호출 후 flush해서 실제 SQL이 실행되게 한 다음 예외나 DB 제약 위반을 일으켰습니다. 트랜잭션 종료 후 새 조회에서 거래가 없고 잔액이 원래 값인지 확인합니다. 단순히 Repository mock 호출 여부만 확인하는 것보다 실제 롤백 동작을 검증할 수 있습니다.

### 멱등성 키가 있는데 왜 화면도 수정했나요?

기존 화면은 저장 버튼을 누를 때마다 새 키를 만들었습니다. 서버 저장 후 응답만 유실된 경우 새 키로 재전송하면 서버가 다른 거래로 인식합니다. 동일 입력의 재시도는 같은 키를 유지하고, 확인된 성공 후에는 키를 초기화하도록 수정했습니다. 페이지 새로고침 이후의 재시도 보관은 아직 구현하지 않았습니다.

### CI와 CD의 차이는 무엇인가요?

CI는 변경마다 빌드·테스트해 코드를 확인하는 과정이고 CD는 배포 단계까지 이어가는 과정입니다. GitHub Actions에 일반 테스트, PostgreSQL 테스트, 화면 재시도 테스트, Compose 시작 검증을 구성했습니다. 클라우드 배포는 없으며 원격 CI 성공도 실제 실행 결과 확인 전에는 주장하지 않습니다.

### 왜 거래 수정·삭제를 추가하지 않았나요?

이미 저장된 거래에는 등록 전후 잔액 스냅샷이 있습니다. 원본을 덮어쓰거나 삭제하면 변경 이력을 설명하기 어려워집니다. 원본 거래를 참조하는 취소·정정 기록과 중복 취소 방지 정책을 먼저 설계하는 것을 후속 과제로 잡았습니다.

### CSV를 바로 DB에 저장하지 않은 이유는 무엇인가요?

가져오기는 단순 INSERT가 아닙니다. 기존 카테고리 매칭, 중복 제외 여부, 과거 거래를 넣을 때 잔액 스냅샷을 어떻게 다시 계산할지, 일부 오류 시 전체 롤백할지 정책이 필요합니다. 먼저 저장 없는 분석으로 사용자 가치를 제공하고 정책이 정해진 뒤 `TransactionService`를 재사용하는 순서를 선택했습니다.

## 4. STAR 방식으로 설명할 경험

### 동시 지출 문제

- **Situation**: 잔액 10,000원에 7,000원과 5,000원 요청이 동시에 들어오면 둘 다 같은 잔액을 읽을 수 있었습니다.
- **Task**: 잔액이 음수가 되지 않고 거래 스냅샷이 순서대로 연결돼야 했습니다.
- **Action**: 사용자 row를 비관적 락으로 조회하고 잔액 검증부터 거래 저장까지 하나의 트랜잭션으로 묶었습니다.
- **Result**: 동일 사용자 요청은 최신 잔액을 기준으로 처리되고, 최종 잔액과 `balanceBefore` / `balanceAfter` 연결을 통합 테스트로 확인했습니다.

### AI 계산 신뢰성 문제

- **Situation**: 원본 거래 전체를 LLM에 보내 계산과 해석을 모두 맡기면 결과 검증과 비용 관리가 어려웠습니다.
- **Task**: 숫자는 재현 가능해야 하고 AI는 유용한 설명을 제공해야 했습니다.
- **Action**: 공통 `AnalysisService`가 통계를 계산하고 `AiReportService`가 집계 DTO만 프롬프트로 변환하도록 분리했습니다.
- **Result**: DB와 CSV가 같은 숫자를 사용하며, AI 프롬프트도 단위 테스트로 검증할 수 있게 됐습니다.

### 서로 다른 CSV 형식 문제

- **Situation**: 은행·카드사마다 헤더, 인코딩, 구분자, 날짜와 유형 표현이 달랐습니다.
- **Task**: 하나의 고정 포맷만 강요하지 않으면서 오류 위치를 알려줘야 했습니다.
- **Action**: 파싱·매핑·검증 책임을 분리하고 자동 추천 후 사용자 확인 단계를 뒀습니다.
- **Result**: 한글·영문 헤더와 UTF-8·MS949를 처리하며 정상 행과 오류 행을 구분해 임시 분석할 수 있습니다.

## 5. 직접 복습할 개념

- Spring `@Transactional` 전파와 JPA dirty checking
- DB 격리 수준, `SELECT FOR UPDATE`, deadlock과 lock timeout
- 낙관적 락과 비관적 락의 차이
- HTTP 멱등성과 DB 유니크 제약
- `BigDecimal` 생성·scale·rounding
- Entity와 API DTO를 분리하는 이유
- HTTP Session, SecurityContext, CSRF, BCrypt
- Flyway 마이그레이션의 불변성과 배포 순서
- CSV quoting, character encoding, multipart 요청
- 외부 API timeout, retry, circuit breaker, 비동기 처리
- H2와 PostgreSQL 동작 차이, Testcontainers

## 6. 과장하지 말아야 할 부분

- H2 동시성 테스트를 PostgreSQL 운영 검증이라고 말하지 않습니다.
- 로컬 세션 로그인은 운영 수준 회원 시스템 전체가 아닙니다.
- CSV는 현재 임시 분석이며 DB 가져오기는 구현하지 않았습니다.
- AI 리포트는 소비 패턴 설명이지 투자·대출 조언이 아닙니다.
- 대량 트래픽 성능은 측정하지 않았으므로 수치를 만들어 말하지 않습니다.

면접에서는 기술 이름보다 문제, 선택 근거, 검증 방법, 현재 한계, 다음 확장 순서까지 연결해 설명하는 것이 중요합니다.
