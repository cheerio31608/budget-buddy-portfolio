## 2. 프로젝트 핵심 메시지

Budget Buddy는 가계부라는 익숙한 도메인을 사용했지만, 구현 과정에서는 금융권 백엔드에서 중요하게 보는 데이터 정합성과 안정성을 중심에 두었습니다.

거래 생성 API는 단순히 거래 내역을 저장하는 기능이 아니라, 사용자의 잔액을 함께 변경하는 핵심 흐름입니다. 그래서 수입/지출 저장과 잔액 업데이트를 하나의 트랜잭션으로 묶고, 동시에 여러 요청이 들어왔을 때도 잔액이 틀어지지 않도록 비관적 락을 적용했습니다.

또한 네트워크 재시도나 버튼 중복 클릭처럼 실제 서비스에서 자주 발생할 수 있는 상황을 고려해 `idempotencyKey`를 도입했습니다. 같은 요청이 반복되더라도 거래가 중복 생성되지 않도록 처리했고, 각 거래마다 `balanceBefore`, `balanceAfter`를 저장해 거래 전후 잔액을 추적할 수 있도록 했습니다.

## 4. STAR 기법 기반 문제 해결 중심 소개

### Situation

가계부 서비스에서 거래 생성은 단순히 거래 row를 추가하는 작업이 아니었습니다. 수입 거래는 잔액을 증가시키고, 지출 거래는 잔액을 감소시키기 때문에 거래 저장과 잔액 변경이 항상 함께 안전하게 처리되어야 했습니다.

특히 동시에 여러 지출 요청이 들어오는 상황을 고려해야 했습니다. 예를 들어 현재 잔액이 10,000원인 사용자에게 8,000원 지출 요청 두 개가 거의 동시에 들어오면, 두 요청이 모두 같은 초기 잔액을 읽고 각각 성공 처리될 수 있습니다. 이 경우 실제로는 허용되면 안 되는 지출이 승인되고, 잔액 데이터도 신뢰하기 어려워집니다.

또 다른 문제는 중복 요청이었습니다. 클라이언트가 거래 생성 요청을 보냈지만 네트워크 오류나 타임아웃으로 응답을 받지 못하면, 같은 요청을 다시 보낼 수 있습니다. 이 상황을 고려하지 않으면 같은 거래가 두 번 저장되고 잔액도 두 번 차감될 수 있습니다.

### Task

이 프로젝트에서는 거래 생성 API를 중심으로 다음 문제를 해결하고자 했습니다.

- 거래 생성과 사용자 잔액 업데이트를 하나의 원자적 작업으로 처리
- 동시에 여러 지출 요청이 들어와도 잔액 정합성 유지
- 네트워크 재시도 또는 버튼 중복 클릭으로 인한 중복 거래 생성 방지
- 거래 전후 잔액을 스냅샷으로 저장해 추적 가능성 확보
- 잔액 부족, 미래 시점 거래, 카테고리 소유권 위반 등 도메인 규칙 검증
- PostgreSQL 운영 환경과 H2 테스트 환경을 분리하면서도 같은 스키마 흐름 유지

### Action

거래 생성 로직은 Service 계층의 단일 `@Transactional` 경계 안에서 처리했습니다. 요청이 들어오면 사용자와 카테고리를 조회하고, 해당 카테고리가 요청한 사용자의 소유인지 먼저 검증했습니다.

잔액을 변경해야 하는 구간에서는 사용자 row를 비관적 락으로 조회했습니다. 같은 사용자의 잔액을 여러 요청이 동시에 수정하지 못하도록 막고, 먼저 처리된 거래의 결과가 다음 거래의 잔액 검증에 반영되도록 하기 위해서입니다.

잔액 계산 시에는 거래 직전 잔액을 `balanceBefore`에 저장하고, 수입 또는 지출 금액을 반영한 결과를 `balanceAfter`에 저장했습니다. 이렇게 하면 거래가 저장된 이후에도 해당 거래가 어떤 잔액 상태에서 발생했고, 처리 결과 잔액이 어떻게 바뀌었는지 확인할 수 있습니다.

중복 요청 문제는 `idempotencyKey`로 처리했습니다. 같은 키로 이미 생성된 거래가 있다면 잔액 계산과 저장 로직을 다시 실행하지 않고 기존 거래를 반환하도록 했습니다. 이를 통해 네트워크 재시도 상황에서도 서버 상태 변경은 한 번만 발생하도록 만들었습니다.

DB 스키마는 Flyway로 관리했습니다. PostgreSQL과 H2 환경 모두 같은 마이그레이션 흐름을 사용하도록 구성했고, 테스트에서는 H2 프로파일을 사용해 로컬 PostgreSQL 상태와 무관하게 검증할 수 있도록 했습니다.

### Result

그 결과 Budget Buddy는 단순 CRUD 프로젝트가 아니라, 거래 정합성과 운영 상황을 고려한 백엔드 프로젝트로 정리할 수 있게 되었습니다.

- 거래 생성과 잔액 변경을 하나의 트랜잭션으로 처리하여 원자성 확보
- 비관적 락 기반 동시성 제어로 Race Condition 방지
- `idempotencyKey` 기반 중복 요청 방지
- `balanceBefore`, `balanceAfter` 저장을 통한 잔액 변경 이력 추적
- Flyway 기반 스키마 마이그레이션으로 DB 변경 이력 관리
- H2/PostgreSQL 환경 분리를 통한 테스트 독립성 확보
- JUnit 5, Mockito 기반 테스트로 주요 도메인 규칙 검증
- Google Gemini API 연동을 통해 월별 지출 리포트 생성 기능 확장

## 5. Technical Deep Dive

## A. 동시성 이슈와 비관적 락 선택 이유

### 문제 상황

거래 생성 기능에서 가장 먼저 신경 쓴 부분은 동시에 여러 지출 요청이 들어왔을 때 잔액이 정확하게 유지되는지였습니다.

현재 잔액이 10,000원이고 8,000원 지출 요청 두 개가 동시에 들어온다고 가정하면, 단순 조회 후 차감 방식으로는 두 요청이 모두 같은 잔액을 읽을 수 있습니다. 두 요청 모두 잔액이 충분하다고 판단하면, 실제로는 승인되면 안 되는 지출까지 성공 처리될 수 있습니다.

이 문제는 단순한 예외 처리나 조건문 추가만으로 해결하기 어렵다고 판단했습니다. 핵심은 같은 사용자 잔액 row를 여러 트랜잭션이 동시에 읽고 수정하려는 상황이었기 때문에, 잔액 변경 구간 자체를 트랜잭션 차원에서 제어해야 했습니다.

### 고려한 접근

처음에는 `@Transactional`만으로 충분한지 확인했습니다. 하지만 트랜잭션을 사용하더라도 동시에 실행되는 요청이 같은 초기 잔액을 읽는 문제는 남을 수 있습니다. 잔액 검증 로직이 올바르더라도, 검증에 사용한 데이터가 최신 상태가 아니면 결과는 틀어질 수 있습니다.

낙관적 락도 대안으로 볼 수 있지만, 충돌을 사후에 감지하고 재시도 전략을 별도로 설계해야 합니다. 반면 이 프로젝트의 거래 생성 흐름에서는 같은 사용자의 잔액 변경을 순차적으로 처리하는 것이 더 자연스럽다고 보았습니다. 잔액은 이전 거래 결과가 다음 거래 가능 여부에 직접 영향을 주는 데이터이기 때문입니다.

### 해결 방법

Budget Buddy에서는 사용자 잔액을 조회하는 Repository 메서드에 비관적 락(Pessimistic Lock)을 적용했습니다. 거래 생성 트랜잭션이 해당 사용자 row의 락을 획득하면, 잔액 계산과 거래 저장이 끝날 때까지 다른 트랜잭션이 같은 사용자의 잔액을 동시에 수정하지 못하도록 했습니다.

Service 계층에서는 다음 흐름을 하나의 `@Transactional` 안에서 처리했습니다.

1. 요청 사용자 조회
2. 카테고리 존재 여부 및 소유권 검증
3. 사용자 잔액 row에 비관적 락 획득
4. 미래 거래 여부 검증
5. 지출 거래의 경우 잔액 부족 여부 검증
6. `balanceBefore` 저장
7. 잔액 변경 계산
8. `balanceAfter` 저장
9. 거래 저장

### 결과

비관적 락 적용 후 같은 사용자에 대한 거래 요청은 순차적으로 처리됩니다. 먼저 처리된 거래가 잔액을 변경하면, 다음 거래는 변경된 최신 잔액을 기준으로 잔액 부족 여부를 판단합니다.

이를 통해 동시에 여러 지출 요청이 들어와도 잔액이 음수가 되는 상황을 방지하고, 승인된 거래만 정확한 `balanceBefore`, `balanceAfter` 스냅샷과 함께 저장할 수 있었습니다.

## B. 네트워크 재시도로 인한 중복 생성을 막는 멱등성 설계

### 문제 상황

거래 생성 API는 서버 상태를 변경하는 POST 요청입니다. 일반적으로 POST 요청은 같은 요청이 두 번 들어오면 서버에서도 두 번 처리될 수 있습니다.

하지만 실제 서비스에서는 같은 요청이 의도치 않게 반복될 수 있습니다. 클라이언트가 거래 생성 요청을 보냈지만 네트워크 지연이나 타임아웃으로 응답을 받지 못하면, 사용자는 같은 요청을 다시 보낼 수 있습니다.

서버 입장에서는 두 번째 요청만 보고 첫 번째 요청이 실제로 실패했는지, 아니면 성공했지만 응답만 유실됐는지 알기 어렵습니다. 이 상황을 그대로 두면 동일한 지출이 두 번 저장되고 잔액도 두 번 차감될 수 있습니다.

### 설계 목표

목표는 같은 의도를 가진 요청이 여러 번 전달되더라도 서버 상태 변경은 한 번만 발생하도록 만드는 것이었습니다.

이를 위해 거래 생성 요청에 `idempotencyKey`를 포함할 수 있도록 했습니다. 클라이언트는 동일한 거래 생성 시도에 같은 키를 전달하고, 서버는 이 키를 기준으로 이미 처리된 요청인지 확인합니다.

### 해결 방법

거래 생성 로직의 초기에 `idempotencyKey`를 확인했습니다. 같은 키로 저장된 거래가 이미 존재하면 잔액 계산, 잔액 검증, 거래 저장 로직을 다시 실행하지 않고 기존 거래를 반환하도록 했습니다.

새 거래가 정상적으로 생성되는 경우에는 요청의 `idempotencyKey`를 거래 데이터와 함께 저장합니다. 이후 같은 키로 요청이 재전송되면 새 거래를 만들지 않고 기존 거래를 재사용합니다.

이 흐름에서 중요하게 본 점은 중복 요청을 단순 에러로 처리하지 않는 것이었습니다. 클라이언트 관점에서 재시도는 이전 요청의 결과를 다시 확인하려는 동작에 가깝습니다. 이미 성공한 요청이라면 기존 성공 결과를 다시 반환하는 것이 API 사용성과 안정성 측면에서 더 적절하다고 판단했습니다.

### 처리 흐름

1. 거래 생성 요청 수신
2. `idempotencyKey` 존재 여부 확인
3. 같은 키로 생성된 거래가 있으면 기존 거래 반환
4. 기존 거래가 없으면 도메인 검증 수행
5. 잔액 스냅샷 저장
6. 거래 생성 및 `idempotencyKey` 저장
7. 생성된 거래 반환

### 결과

이 설계를 통해 클라이언트는 네트워크 오류 상황에서 안전하게 재시도할 수 있습니다. 서버는 같은 거래 의도를 한 번만 반영하므로 중복 생성과 중복 차감을 방지할 수 있습니다.

Budget Buddy의 멱등성 설계는 단순 API 구현을 넘어 실제 운영 환경의 재시도 상황을 고려했다는 점에서 의미가 있습니다. 특히 금융권 백엔드에서 중요하게 보는 데이터 일관성, 재시도 안전성, 중복 처리 방지에 대한 이해를 보여줄 수 있는 부분이라고 생각합니다.

## 6. 설계 관점 요약

### 동시성 제어

거래 생성 로직은 `@Transactional`만 적용하는 데서 끝내지 않고, 같은 사용자 잔액 row에 대한 동시 변경 문제를 별도로 다뤘습니다. 비관적 락을 통해 잔액 변경 구간을 직렬화하고, 최신 잔액 기준으로 거래 가능 여부를 판단하도록 했습니다.

### 감사 가능성

거래 후 현재 잔액만 유지하는 구조가 아니라, 각 거래마다 `balanceBefore`, `balanceAfter`를 저장했습니다. 이를 통해 특정 거래가 어떤 잔액 상태에서 발생했고, 처리 결과가 어떻게 반영되었는지 추적할 수 있도록 했습니다.

### 멱등성

거래 생성 POST 요청의 중복 실행 위험을 고려해 `idempotencyKey`를 도입했습니다. 네트워크 재시도 상황에서도 서버 상태 변경이 한 번만 발생하도록 하여 중복 거래 생성과 중복 잔액 차감을 방지했습니다.

### 테스트 가능성

H2 테스트 프로파일과 Flyway 마이그레이션을 활용해 로컬 PostgreSQL 의존성을 줄였습니다. 서비스 테스트와 통합 테스트를 통해 잔액 변경, 잔액 부족, 스냅샷 저장, 동시성 흐름을 검증했습니다.
